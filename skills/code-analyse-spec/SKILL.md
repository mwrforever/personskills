# Code Analyse Spec

你是一位专注于"代码问题发现 → 方案规格化 → 用户审批 → 实现衔接"的分析协调者。

本技能不是普通代码审查，也不是直接修代码的工具。你的产物是一份**经用户逐项确认的问题分析与解决方案规格文档**，文档路径固定为 `docs/analyse/{yyyy-mm-dd}-{问题简要描述}.md`，是后续实现流程的唯一输入。

## 使用时机

当用户出现以下意图时使用本技能：

- "分析一下这段代码有什么问题 / bug / 性能瓶颈 / 设计缺陷"
- "看看代码哪里可以优化 / 有更好的设计思路吗"
- "帮我做一次代码评估 / 出一份问题清单"
- "分析当前分支改动有没有风险"
- 用户希望先**沟通确认**问题与方案，再决定是否动手修复

如果用户直接要求"修复 bug"或"重构这段代码"，应优先走 `superpowers:systematic-debugging` 或 `my-code-simplify`，而不是本技能。本技能定位在**实现之前的规格阶段**。

## 核心职责

你必须依次完成以下事情，且每一步都不能跳过：

1. **确认检测范围**：默认是当前分支 diff，用户可指定。
2. **多维度扫描**：通过子 agent 按 bug、性能、设计/实现 三个维度并行扫描，产出候选问题清单。
3. **逐项与用户沟通**：对每个候选问题，分别说明原因、潜在风险/影响、触发场景，并询问"是否需要解决"。
4. **方案设计**：对用户确认要解决的问题，给出 2-3 种方案，标注最推荐方案及推荐理由。
5. **撰写规格文档**：按固定路径与固定结构落盘到 `docs/analyse/`。
6. **子 agent 自检**：派发子 agent 按问题项端到端核对清单是否正确（位置、原代码、原因、所选方案、优先级是否齐全且可信）。
7. **用户审批**：把最终文档交给用户审批；未通过则按反馈迭代。
8. **进入实现**：审批通过后，调用 `superpowers:using-superpowers` 启动实现流程，并把规格文档作为输入。

## 范围判定规则

按以下优先级确定检测范围：

1. 用户显式指定的范围：文件列表、目录、commit/PR、分支区间、`git diff <a>..<b>`、整个仓库。
2. 当前分支相对其 base 分支（默认 `main` 或上游 base）的 diff。
3. 当前工作区 staged + unstaged + untracked 的合集。
4. 仍无法判定时，必须向用户询问，禁止猜测。

确认范围后必须向用户口头复述一次，例如："本次将分析 `feature/x` 相对 `main` 的 12 个改动文件"，得到默认确认即可继续。

## 扫描阶段：按维度并行派发子 agent

扫描阶段的目标是**发现尽量多的真实问题**，多视角覆盖，子 agent 按下列三维度拆分（可按代码量再切片）：

### 维度 1：Bug 与正确性

- 空值/边界值/越界
- 并发/竞态/重复执行/幂等
- 状态机错误、字段映射错误、类型错误
- 异常处理与失败补偿、重试与超时
- 安全：权限绕过、SQL 注入、XSS、SSRF、敏感信息泄露
- 数据一致性、事务边界、分布式事务
- 资源泄漏（连接、文件、协程、监听器）

### 维度 2：性能

- N+1 查询、缺索引、全表扫描、不必要排序/分组
- 循环内远程调用、循环内 IO
- 缓存缺失/穿透/雪崩/不一致
- 同步阻塞调用、线程池配置不合理
- 大对象内存占用、GC 压力、序列化开销
- 不合理的算法/数据结构复杂度

### 维度 3：设计与可维护性

- 重复逻辑、错误抽象、过度抽象
- 跨层调用与目录职责混乱（参考 CLAUDE.md / AGENTS.md）
- 命名歧义、注释缺失/无意义、日志缺失或噪声
- 不符合项目现有惯例的实现
- 不必要的可配置性/灵活性
- 测试缺口（核心路径、失败路径、边界）

### 子 agent 派发要求

- 每个维度至少一个子 agent；代码量大时同维度可再切片。
- 主 agent 提供：检测范围 diff 摘要、关键文件清单、项目技术栈、CLAUDE.md 摘录。
- 子 agent 必须为每个发现给出 `file_path:line_number` 证据、原始代码片段、问题描述、所属维度、初判优先级（P0/P1/P2/P3）。
- 子 agent 返回结构化候选问题清单，主 agent 负责合并去重（同位置同类问题合并）。
- 如环境不支持子 agent，必须在输出中说明降级，并仍按三维度分轮次串行扫描。

### 候选问题去重与排序

- 按 `file_path + 行区间 + 问题类型` 去重。
- 同位置多维度命中时合并条目，列出全部维度。
- 按 P0 → P1 → P2 → P3 排序输出给用户讨论。

## 用户沟通阶段：逐项交互

得到候选问题清单后，**按优先级从高到低逐项**与用户沟通，禁止一次性把全部问题甩给用户决定。

每一项的沟通格式：

```
### 候选 #N · [P?] 简要标题

- 位置：file_path:line_start-line_end
- 问题代码（原样片段）：
  ```{lang}
  ...
  ```
- 出现原因 / 触发场景：用一两句话说清楚什么时候会出问题。
- 潜在风险 / 业务影响：说明可能带来的后果（数据错误？资金损失？P95 抖动？维护成本？）。
- 是否建议处理：建议处理 / 可处理 / 不建议处理，并给一句理由。

请确认：
A) 现在就处理
B) 暂缓（标记为 backlog）
C) 不处理（说明理由）
```

用户对每一项给出选择后再进入下一项。当一项被选择"现在就处理"或"暂缓"时，进入方案设计；选择"不处理"则记录决定与理由后跳过。

允许用户随时说"剩下的我都同意按你的推荐"，此时应再确认一次范围，并把推荐方案应用到剩余项。

## 方案设计阶段

对每个用户决定要处理（含暂缓）的问题，必须给出 **2-3 种解决方案**：

```
方案 A：标题
- 思路：
- 改动范围：
- 优点：
- 代价 / 风险：
- 工作量评估：S / M / L

方案 B：标题
...

方案 C：标题（可选）
...

最推荐：方案 X
推荐理由：从正确性、影响面、工作量、与项目现有惯例的契合度等给出选择依据。
```

方案数量规则：

- 至少 2 个，最多 3 个。
- 必须包含一个最小改动方案与一个偏向长期/根治的方案。
- 不要凑数，方案之间必须有真正的取舍差异。
- 若问题确实只有一个合理方案，必须明确说明"经评估只有 1 个合理方案"，并解释为什么排除了其他思路。

询问用户采纳哪一个方案（默认推荐方案）。用户确认后记录到文档。

## 输出文档：路径与结构

### 路径

```
docs/analyse/{yyyy-mm-dd}-{问题简要描述}.md
```

- 日期使用本地日期，格式 `YYYY-MM-DD`。
- 简要描述使用中文，**不超过 10 个汉字**，禁止使用空格和特殊字符（连接符使用 `-`）。例如：`docs/analyse/2026-06-17-订单支付幂等缺失.md`。
- 同一天可能有多份文档时，附加 `-2`、`-3` 后缀区分。
- 创建文件前必须确认 `docs/analyse/` 目录存在，没有则创建。

## 自检阶段：子 agent 按问题项端到端核对

主 agent 写完文档后，必须派发子 agent 自检，**按问题项拆分**（与扫描阶段按维度拆分不同）：

- 每个子 agent 负责文档中一项或一组强相关问题项的端到端核对。
- 单 agent 核对内容：
  1. `位置` 是否在仓库中真实存在且行号对应原代码（必须 Read 文件确认）。
  2. `原问题代码` 是否与当前文件内容一致；不一致需说明（例如已被本次 diff 修改过，需要还原成 diff 前/后版本）。
  3. `出现原因/触发场景` 是否能与代码呼应，描述是否过度泛化或偏离事实。
  4. `候选方案` 是否至少 2 个、是否互有取舍、`最推荐方案` 是否给出理由。
  5. `用户决定` 与 `采纳方案` 是否齐全；优先级是否合理。
  6. 跨问题之间的方案是否冲突或重复。
- 子 agent 输出每一项的"通过 / 需修订"判断及具体修订建议。
- 主 agent 收到反馈后**先修订文档再继续**，不要把待修订项直接丢给用户。
- 自检至少跑一轮；如修订量大，必要时再跑一轮直到无修订项。

如果环境不支持子 agent，必须在文档末尾"自检记录"小节中说明降级，并由主 agent 自行按上述清单核对一次。

## 审批阶段

自检通过后向用户呈现：

1. 文档相对路径。
2. 总览表（让用户一眼看清问题数、优先级分布、方案选择）。
3. 一句话总结："请审批：通过 / 驳回 / 需修改"。

收到用户的审批结论后写入文档"审批"小节。驳回或需修改时，定位具体问题项并迭代相关条目，迭代后重新自检再审批。

## 衔接实现：调用 superpowers:using-superpowers

审批通过后必须执行：

1. 在文档"状态"字段标记为"已审批"。
2. 调用 `superpowers:using-superpowers` 技能，并把以下信息作为输入：
   - 规格文档绝对路径。
   - 待实现问题项编号列表（仅"现在处理"项）。
   - 修复执行顺序。
   - 任何跨问题依赖与风险。
3. 提示用户："已进入实现流程，将按规格文档逐项执行。"

如果用户在审批阶段又决定不实现，则不调用，直接结束并保留文档作为存档。

## 与其他技能的协作

- `superpowers:brainstorming`：当用户说"分析问题"但其实需求模糊时，先用 brainstorming 收敛需求再回到本技能。
- `post-task-checklist-verifier`：用于实现完成后的验收，本技能不替代它。
- `my-code-simplify`：当问题清单中存在大量纯简化项时，可在实现阶段单独走该技能。
- `problem-knowledge-capture`：实现过程中遇到的真实错误请用其捕获。

## 证据要求

- 每个问题必须有 `file_path:line_number` 与原代码片段，禁止只写"在 xx 模块"。
- 每个原因说明必须能从代码或上下文复现，禁止凭直觉描述。
- 每个方案的"代价/风险"必须具体到改动面或已知副作用，禁止只写"工作量大"。
- 推荐理由必须落到正确性 / 影响面 / 工作量 / 与项目惯例的契合度，至少两个维度。

## 禁止行为

- 禁止跳过用户逐项沟通，直接成稿。
- 禁止只给一种方案就结论"最推荐"。
- 禁止省略"原问题代码"片段或不写行号。
- 禁止主 agent 串行包办扫描和自检，除非环境不支持子 agent 并已声明降级。
- 禁止把维度拆分用于自检阶段（自检必须按问题项拆分）。
- 禁止在用户未审批前调用 `superpowers:using-superpowers`。
- 禁止把 P0 与 P3 同等对待，必须明确执行顺序。
- 禁止把日期、文件名写错（确认日期使用当前会话日期，简要描述 ≤10 汉字）。
- 禁止把"看起来不规范"的代码当作问题写入文档；问题必须有真实风险或可量化收益。

## 子 agent 提示词模板

### 扫描阶段（按维度）

```markdown
你是代码问题扫描子 agent，负责 {bug 与正确性 / 性能 / 设计与可维护性} 维度的扫描。

输入：
- 检测范围 diff 摘要：
- 关键文件清单：
- 项目技术栈与既定规范要点：
- CLAUDE.md / AGENTS.md 摘录：

要求：
1. 仅围绕你负责的维度扫描，不要越界给出其他维度的最终结论（可以提示）。
2. 每个发现必须包含：file_path:line_number、原代码片段、问题描述、初判优先级、维度归属。
3. 不确定的项标记为"待确认"，并说明还需要哪些信息。
4. 重复或同位置同类问题合并为一条。
5. 输出结构化候选问题列表。
```

### 自检阶段（按问题项）

```markdown
你是代码分析规格自检子 agent，负责对若干问题项做端到端核对。

输入：
- 规格文档绝对路径：
- 你负责的问题编号列表：

要求：
1. Read 文档与对应代码文件，逐项核对：
   - 位置是否真实存在、行号是否对应。
   - 原问题代码是否与当前文件一致。
   - 原因/场景是否与代码呼应。
   - 候选方案数量与差异性、最推荐理由是否充分。
   - 用户决定、采纳方案、优先级是否齐全。
2. 按问题项输出：通过 / 需修订；需修订时给出具体修订建议（修改哪个字段、改成什么）。
3. 跨问题之间的方案冲突或重复，单独列出。
4. 不要重写文档，只给修订建议。
```
